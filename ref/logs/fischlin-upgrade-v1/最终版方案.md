# 最终版方案

> 适用阶段：临近交稿，以“完整跑通、可复现实验、表述不过界”为第一优先级。  
> 本文用于冻结毕业设计后续路线，停止继续追求“Fischlin 三关系完整 STARK 内生化”终态，转而保证可以稳健声明：  
> `我实现了一个能完整运行的、基于 Fischlin 框架的后量子盲签原型系统。`

## 1. 题目评估

当前题目：

- `面向零知识证明的 SPHINCS+-like 盲签名设计与实现`

总体评价：

- 这个题目可以用，优点是口径安全、包容度高，不会把你绑定到“完整 Fischlin 内生”或“完整形式化安全证明”。
- `面向零知识证明` 这几个字允许你把 STARK 部分写成“验证增强/可验证关系约束模块”，而不必证明整个系统已经完全零知识内生闭环。
- `SPHINCS+-like` 也比直接写“标准 SPHINCS+”更稳妥，因为你做的是 `Poseidon2` 替换后的变体与工程实现。

建议的保守版题目：

- `面向零知识验证的 SPHINCS+-like 盲签名设计与实现`
- `基于 Poseidon2 的 SPHINCS+-like 盲签名方案设计与实现`
- `基于 Fischlin 框架的 SPHINCS+-like 后量子盲签名设计与实现`

建议的最佳折中题目：

- `基于 Fischlin 框架的 SPHINCS+-like 后量子盲签名设计与实现`

原因：

- 直接点出 Fischlin 框架，能体现你的协议来源。
- 保留 `SPHINCS+-like`，避免对“完全标准 SPHINCS+”作过强承诺。
- 不要求你在标题层面承诺“完整零知识内生证明系统”。

如果你特别想保留“零知识证明”关键词，建议改为：

- `面向零知识验证的基于 Fischlin 框架的 SPHINCS+-like 盲签名设计与实现`

不建议使用的题目：

- `Fischlin 盲签方案的完整设计与实现`
- `基于 STARK 的 Fischlin 盲签完整内生化实现`
- `标准 Fischlin 后量子盲签方案设计与实现`

原因：

- 这些题目默认你完成了完整密码学语义闭环、完整安全口径和完整 STARK 内生化，当前阶段风险过高。

## 2. 最终成果定位

本课题最终成果的安全表述应冻结为：

- `本文实现了一个基于 Fischlin 框架的、可完整运行的后量子盲签原型系统。`
- `本文在 Poseidon2 替换底层哈希的 SPHINCS+-like 结构上，完成了盲签协议全流程的设计、实现与实验验证。`
- `本文进一步引入 STARK 机制对部分关键关系进行约束增强，但未将全部密码学关系完全内生化到统一 AIR 中。`

本课题不应声称：

- `本文完成了标准 Fischlin 盲签方案的严格等价实现。`
- `本文完成了 Fischlin 三关系的完整 STARK 内生化。`
- `本文已经给出完整形式化安全归约并完成终态证明系统实现。`

## 3. 可声明成果边界

只要满足以下条件，即可安全声明你完成了“基于 Fischlin 框架的后量子盲签原型系统”：

- 完整协议主流程可运行：`Issue -> Unblind -> Show -> Verify`。
- 公开输入和见证口径稳定，至少能说明 `pk_sig / pk_E / m_pub / public_ctx / r / omega2 / sigma'` 在系统中的角色。
- `Poseidon2` 已实际替换到底层 `SPHINCS+-like` 哈希相关路径，而不是停留在文档描述。
- 负例测试证明关键篡改会被拒绝，至少包括 `m_pub / r / pk_sig / sigma' / pk_E / omega2 / public_ctx`。
- STARK 部分有实际实现与实验结果，但在论文中明确定位为“部分关系约束增强”。

## 8. 必须拿到的实验数据

本节是交稿最关键部分。没有完整实验表，题目再稳也不够。

### 8.1 功能正确性实验

至少统计以下内容：

- `Commit` 成功率
- `Issue` 成功率
- `Unblind` 成功率
- `Show` 成功率
- `Verify` 成功率
- `Issue -> Unblind -> Show -> Verify` 全流程成功率

建议做法：

- 固定参数组，重复运行 `30` 次或 `50` 次。
- 记录成功次数、失败次数、失败原因。

### 8.2 篡改拒绝实验

至少覆盖以下负例：

- `m_pub` 篡改
- `r` 篡改
- `pk_sig` 篡改
- `sigma'` 篡改
- `pk_E` 篡改
- `omega2` 篡改
- `public_ctx` 篡改
- `sigma_c` 篡改
- 缺失 `m_pub`
- 缺失 `omega2`

建议记录字段：

- 篡改项
- 触发阶段
- 期望结果
- 实际结果
- 错误码或失败相位

### 8.3 性能实验

至少统计以下平均时间：

- `Commit` 时间
- `Issue / Blind Sign` 时间
- `Unblind` 时间
- `Show` 时间
- `Verify` 时间

若使用 STARK，还应统计：

- `prove` 时间
- `verify` 时间
- proof 序列化大小

建议记录：

- 平均值
- 最小值
- 最大值
- 标准差

### 8.4 空间与对象大小实验

至少记录：

- 公钥大小
- 秘钥大小
- `com` 大小
- `sigma'` 或 credential 大小
- `sigma_C` 大小
- `pi_f_v2` 大小
- 最终 show 输出对象大小

### 8.5 对比实验

如果时间允许，至少做一个最小对比：

- 原始 SPHINCS+ 路径 vs `Poseidon2-SPHINCS+-like` 路径

可比较项：

- 签名时间
- 验签时间
- 输出大小

如果做不了完整对比，至少给出：

- 当前 `Poseidon2-SPHINCS+-like` 参数组下的绝对性能数据
