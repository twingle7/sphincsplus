## 创新点框架

### 一、密码学层面创新

#### 1.1 Poseidon2 对 NIST 标准哈希签名方案的系统性替换

- **问题**：SPHINCS+（FIPS 205）、XMSS/HSS（SP 800-208）等 NIST 标准化哈希签名方案依赖 SHA-256/SHAKE-256 作为底层哈希。在 STARK/SNARK 电路中，SHA-256 单次压缩函数需约 25,000 个 R1CS 约束，SPHINCS+ 验证路径约 2,000 次哈希调用，总计约 50,000,000 约束——远超实际证明能力。
- **方案**：使用 Goldilocks 素数域（p = 2^64 - 2^32 + 1）上的 Poseidon2 海绵构造（t=12，capacity=6，rate=6，RF=8，RP=22，共 30 轮）全量替换上述方案的底层可调哈希函数（THF），将每次置换的约束降至约 300 个（R1CS）或 53 个（全内生 AIR）。
- **关键设计决策**：
  - Goldilocks 域选择：64-bit 友好，适合 C uint64_t 和 STARK 算术化，2^32 阶单位根支持 FFT
  - 域分离策略：6 种 domain tag（PRF_ADDR=0x10、GEN_MESSAGE_RANDOM=0x0F、HASH_MESSAGE=0x0E、THASH_F=0x11、THASH_H=0x12、THASH_TL=0x13）确保不同类型哈希调用不可混淆
  - 字节到 lane 编码：pad10*1 + 64-bit 小端序打包，匹配 C 层 `poseidon2_inc_absorb` 的语义
- **与现有方案区别**：SPHINCS+-SM3（《密码学报》2023）替换 SHA-256 为另一个传统哈希 SM3，目标为国密合规而非 ZK 证明效率。本方案的替换目标是将 NIST 标准哈希签名方案的验证电路复杂度从 ~50M 约束降至 ~600K 约束（约 80 倍），使 STARK 证明实用化。

#### 1.2 THF 语义的完整保持与安全继承

- SPHINCS+ 安全证明依赖 THF 的四个性质（SM-TCR / SM-DSPR / SM-PRE / SM-UD），在 ROM 下紧致归约
- Poseidon2 替换后保持了 `pub_seed || ADRS || M` 的完整 THF 语义，域标签提供域分离，ADRS 提供多目标防护
- 安全参数选择遵循 SPHINCS+ 规范的方法论，签名预算 q_s 从 2^64（规范保守假设）调整为 2^16--2^20（盲签名场景），FORS 安全项增大约 20 比特
- 30 轮 Poseidon2 远超已知攻击阈值（统计饱和攻击 ~18 轮、Gröbner 基攻击 ~14 轮、差分攻击 ~16 轮）

#### 1.3 多方案通用适配

- 三种 NIST 标准哈希签名方案共享同一套 Poseidon2 置换（RF=8+RP=22，t=12），验证路径差异仅在于 FORS 层的有无：

| 方案 | 标准 | 验证路径特征 | 适配方式 |
|------|------|------------|---------|
| SPHINCS+ | FIPS 205 | H_msg → FORS → WOTS+ → Merkle | 完整跟踪构建 |
| XMSS | SP 800-208 | H_msg → WOTS+ → Merkle | 跳过 FORS 层 |
| XMSS^MT / HSS | SP 800-208 | H_msg → (WOTS+ → Merkle) × N 层 | 跳过 FORS + 多层级迭代 |

- **AIR 约束层完全复用**——53 条约束在所有方案间一致，仅执行跟踪构建器需适配参数配置和 FORS 层的有无
- 这种通用性源于 Poseidon2 作为统一底层置换的设计——所有方案的 THF 调用均映射到相同的海绵吸收-挤压操作

### 二、协议层面创新

#### 2.1 Fischlin 框架在 NIST 标准哈希签名上的首次完整实例化

- Fischlin（CRYPTO 2006）是通用盲签名框架，此前实例化多基于 RSA/离散对数/格
- Bouillaguet 等人（IEEE S&P 2026）从理论上证明任意 Hash-and-Sign 签名可编译为 Fischlin 盲签名，但仅实现了 UOV（多元）和 Wave（编码基）的实例化，**未实现 SPHINCS+ 实例化**
- Herranz 和 Louiso（ePrint 2025/2097）首次探索了哈希基盲签名可行性，但使用 MSS（有状态 Merkle 签名方案）+ ZKBoo（MPC-in-the-Head 变体），**未使用 SPHINCS+ 和 STARK**
- 本方案的特殊技术挑战：
  - SPHINCS+ 的非平凡 witness 结构（多层 Merkle 超树 + FORS 多树 + WOTS+ 多链）使 Fischlin 实例化有实质性工程难度
  - 承诺方案使用 Poseidon2 海绵哈希（基于域运算，非代数群结构）
  - sigma_C 密文构造将 SPHINCS+ 签名嵌入类密文结构：`sigma_C = Poseidon2_Sponge(pk_E || com || sigma_com || omega2)`
  - 展示证明使用全内生 STARK AIR（而非 Fischlin 原始框架中的通用 NIZK 或 Bouillaguet 的 MPC-in-the-Head）

#### 2.2 Statement-Bound 模式与上下文绑定

- 在标准 Fischlin 框架外增加了 Statement-Bound 变体
- 将展示绑定到显式公开声明：pk_E、m_pub、public_ctx
- ctx_hash = Blake3(pk_sig || pk_E || com || m_pub || public_ctx || sigma_C)，296 字节嵌入 proof header
- 防跨上下文重放 + 半盲签名支持的工程基础

### 三、工程/系统层面创新

#### 3.1 全内生 AIR 的 STARK 证明生成方法 ⭐⭐⭐ （核心技术创新）

**核心理念：执行跟踪即验证过程（Trace IS Verification）。** 跟踪构建器遍历签名验证算法的完整执行路径，将每一步 Poseidon2 置换展开为跟踪行。AIR 约束仅需验证"跟踪中的下一状态等于预计算的期望状态"。证明跟踪正确 = 证明验证通过——无需任何外部 C 语言 guard。

**技术方案——预计算期望状态（Pre-computed Expected Next State, PENS）：**

1. 跟踪构建器模拟 `crypto_sign_verify` 完整执行：H_msg 消息哈希 → FORS 签名验证 → WOTS+ 链验证 → 超树 Merkle 路径验证
2. 每轮 Poseidon2 运算对应跟踪中一行，记录当前 12 个状态通道、轮次计数器、置换索引、调用类型、填充标记
3. 构建跟踪的同时调用 `poseidon2_round()` 预计算下一状态的期望值，存储在跟踪列 16-27
4. AIR 仅需简单等值约束 `nxt == expected`——全部 53 条约束的代数度数均为 1

**53 条 AIR 约束分类：**

| 约束组 | 数量 | 内容 |
|--------|------|------|
| ① 核心置换约束 | 16 | 全轮/部分轮的 rate lanes（x^7 S-box + MDS）+ capacity lanes |
| ② 吸收绑定约束 | 12 | THASH absorb[0..5] 绑定到 domain + pub_seed + ADRS 字节 |
| ③ 状态携带约束 | 12 | 跨置换块的海绵状态连续性（init_state + carries_from_prev / carries_to_next） |
| ④ THASH 吸收验证 | 8 | 域标签一致性 + 地址一致性 + 输入来源验证 |
| ⑤ 布尔约束 | 4 | pad flag、轮次计数器 MSB 等布尔值约束 |
| ⑥ 复制/边界约束 | 3 | com_output 行断言、root_row 断言（pk_root）、ctx_hash 公开输入绑定 |

**边界断言（6 条）：** 初始状态/轮次/置换索引、最终状态、根节点 = PK.root、承诺输出 = com。

**关键指标（128-bit 安全级，n=16, h=63, d=7, k=10, a=12, w=16）：**

| 指标 | 数值 |
|------|------|
| 执行跟踪规模 | 23,861 行 × 64 列（有效行），next pow2: 32,768 |
| Poseidon2 置换总数 | 2,091 次 |
| AIR 约束总数 | 53 条（全部度数为 1） |
| 列利用率 | 58/64 (91%) |
| 证明生成时间 | ~37 秒 |
| 证明体积 | ~85 KB |
| 验证时间 | ~4 毫秒 |
| 内存峰值 | ~4.6 GB |
| FRI 参数 | blowup=16, queries=27, ~108-bit 猜想安全性 |

**新增技术点（2026年7月）：**

1. **海绵状态连续性（Sponge State Continuity）**：跟踪列 39-52 存储跨置换块的海绵状态传递。carries_from_prev / carries_to_next 标志控制状态传递方向，init_state 列存储每个置换块的初始状态。AIR 约束确保相邻置换块之间的海绵状态不丢失——这是将 C 层面向对象的状态管理（`poseidon2_t`）映射到二维跟踪矩阵的关键创新。

2. **THASH 吸收绑定（Absorb Binding）**：约束 45-52 确保 absorb[0] 绑定到 domain tag + pub_seed（通过 Lagrange selector 在 THASH 第一行检查），absorb[1] 绑定到 pub_seed_hi（对 THASH 首个置换的每行检查），absorb[2..5] 绑定到预期的 ADRS 字节（与跟踪构建器预计算值匹配）。这防止了跨公钥伪造和跨地址重放。

3. **pk_root 边界断言**：在超树根行（root_row），AIR 约束断言 `computed_root = pk_sig.root`。这确保证明中计算出的 Merkle 根与签发者公钥中的根值完全一致——即使全部 2,091 个 Poseidon2 置换都正确执行，若最终根不匹配，证明仍会失败。

4. **Proof header v2**：魔数"PFP2"（0x32504650）+ 版本号 2，ctx_hash 绑定 296 字节头部。在验证时重新计算并比对 ctx_hash，防止跨上下文重放。

#### 3.2 成本模型驱动的参数搜索

- 解析公式：`total_perms = H_msg + FORS + HT`
- `trace_rows = next_pow2(total_perms × 32)`
- `prove_seconds ≈ 127 × (trace_rows/131,072) × (log₂(trace_rows)/17)`
- ~3.5% 误差（vs 实际 benchmark），支持 M1→M2→M3→M4 四阶段搜索流程
- 128 位档 Pareto 前沿 24 个候选，4 组推荐参数（p2-128f / p2-128cs / p2-128s / p2-128）

#### 3.3 C/Rust FFI 双语言架构

- C 层（~15,000 行）：SPHINCS+ 核心签名 + Poseidon2 置换 + Fischlin 协议流 + witness 构造 + 测试框架
- Rust 层（~5,000 行）：Winterfell STARK prover/verifier + Full-AIR 约束定义（air_engine.rs）+ 执行跟踪构建器（trace_builder.rs）+ FFI 导出
- FFI 层（~500 行）：`extern "C"` 接口 + ABI 版本检查 + 结构化错误码映射
- 支持 `spx_p2_ffi_generate_pi_f_full_air()` / `spx_p2_ffi_verify_pi_f_full_air()` 两路径

## 与最相近已有工作的区分

| 特征 | Bouillaguet et al. (IEEE S&P 2026) | Herranz & Louiso (ePrint 2025) | 本方案 |
|------|-------------------------------------|-------------------------------|--------|
| 底层签名 | UOV / Wave（多元/编码基） | MSS（有状态 Merkle） | **SPHINCS+ / XMSS / XMSS^MT / HSS**（NIST 标准） |
| ZK 技术 | MPC-in-the-Head (TCitH) | ZKBoo/ZKB++ (MPCitH) | **STARK（全内生 AIR）** |
| 盲签名 | ✅（Fischlin 编译器） | ✅（Fischlin 框架，原型） | ✅（Fischlin + Statement-Bound） |
| 约束数 / 电路规模 | ~数万门电路 | ~数万门电路（估算） | **53 条 AIR 约束（全部度数为 1）** |
| 证明方式 | CAP + MPCitH | MPCitH 模拟 | **全内生 trace（PENS 方法）** |
| 哈希函数 | 原生方案哈希 | 通用哈希（SHA-256） | **Poseidon2（Goldilocks 域原生，ZK 友好）** |
| 半盲签名 | 未讨论 | 未讨论 | **ctx_hash 机制支持** |
| 实现完整度 | UOV/Wave 实例化 | 电路估算，无端到端 | **完整 C+Rust 原型 + 9 项回归测试** |

**与本方案最接近的独立工作是 Herranz & Louiso (ePrint 2025/2097)**——同为仅依赖哈希碰撞抗性的盲签名。核心区别在于：
1. 底层签名：MSS（有状态） vs. SPHINCS+ / XMSS / XMSS^MT / HSS（NIST 标准，SPHINCS+ 为无状态）
2. 证明系统：ZKBoo（MPCitH） vs. Winterfell STARK（全内生 AIR）
3. 哈希函数：通用哈希（SHA-256） vs. Poseidon2（ZK 友好，在 STARK 电路中仅 53 条约束）
