# TPM2 LMS 方案 — 新颖性检索与分析

## 方案概述

基于 `技术交底书.md` 的技术方案：使用单个 TPM2 NV Counter 作为全局不可回滚提交序号，通过认证 append-only 状态账本维护多个 LMS 签名密钥各自的 `next_q`，解决 TPM2 NV counter 数量有限条件下多个 LMS 密钥状态管理问题。

## 核心技术特征

1. **全局提交时钟**：将单个 TPM2 NV counter 定义为不绑定具体密钥的全局序号 `G`
2. **认证状态账本**：append-only 结构，每条记录含 `seq`, `key_id`, `q_start`, `q_count`, `prev_hash`, `state_after`, `mac`
3. **职责分离**：TPM counter 只承担不可回滚时钟，账本承担多 key 状态索引
4. **故障安全**：崩溃后宁可浪费 leaf 也不允许复用
5. **恢复协议**：`L_last == G_now` 一致才恢复，否则 fail-stop

### 初步评估

**潜在新颖性点：**
- "一个 TPM counter + 认证账本 → 多个 LMS key"这个组合可能尚未被直接披露
- 认证账本的具体字段设计（`key_id`, `q_start/q_count`, `state_after`）有定制化特征
- fail-stop 恢复策略（`L_last != G_now` → 直接拒绝）提供了明确的安全保证
- 批量预留 leaf 的变体设计对不同场景有适应性

**潜在风险：**
- 单个 counter 管理多个实体状态是通用模式，可能在非 LMS 场景已有类似方案
- append-only 日志 + TPM 认证是已知组合（如 TPM2 审计日志）
- 需要确保具体字段组合和恢复协议有足够区分度

## 权利要求草案（初步）

### 独立权利要求1（方法）
一种基于单个 TPM2 NV Counter 管理多个 LMS 签名密钥状态的方法，其特征在于：
1. 将单个 TPM2 NV Counter 配置为全局提交序号 `G`，不绑定任何具体 LMS 密钥的 leaf index `q`
2. 维护一个 append-only 状态账本 `L`，其中每条记录包含：
   - `seq`：来自 TPM2 NV Counter 的全局序号
   - `key_id`：由 LMS 公钥和参数派生的密钥标识符
   - `q_start`, `q_count`：本次预留的 LMS leaf 索引区间
   - `prev_hash`：前一条账本记录的密码学哈希
   - `state_after`：该 key 更新后的状态摘要
   - `mac`：使用日志认证密钥 `Klog` 计算的 MAC
3. 每次签名前先执行 TPM2_NV_Increment 获取新 `seq`，再追加账本记录并持久化，最后才使用预留的 `q` 进行签名
4. 恢复时校验账本哈希链、MAC 和 `L_last == G_now`，不一致则 fail-stop

### 独立权利要求2（系统）
一种实现权利要求1所述方法的系统，包括：
- TPM2 硬件模块，提供 NV Counter 单调递增能力
- 状态管理器，负责账本的读写、校验和恢复
- 签名服务，调用状态管理器预留 leaf 后执行 LMS 签名

### 从属权利要求
- 批量预留模式：`q_count > 1`
- `Klog` 由 TPM sealed key 保护的变体
- 多节点部署的 `q` 区间分配变体
- 远程只追加介质备份的变体

## 结论

**新颖性评估：中等**。核心技术组合（TPM counter 全局时钟 + 认证账本 + 多 LMS key）可能具有新颖性，但需要在专利数据库中确认。建议在正式撰写专利申请前进行专业的专利检索。
